# Ранжирование фрагментов ответов: Jina v2 + RankNet

## 1. Задача и данные

Для каждого англоязычного запроса задан набор фрагментов ответов. Модель присваивает каждой паре «запрос — фрагмент» числовую оценку, по которой релевантные фрагменты должны располагаться выше нерелевантных.

Обучающая выборка содержит **31 530 пар и 3 042 запроса**. Доля релевантных пар — **25,91%**. В модель передаются запрос и документ, состоящий из заголовка и содержания фрагмента. Метаданные статьи не используются как отдельные признаки.

Целевая метрика — **средняя по запросам NDCG@10**. Результат работы — CSV с колонками `id,prediction`. Чем больше прогноз, тем выше кандидат должен находиться в выдаче.

Итоговая предобработка заполняет отсутствующие заголовки пустой строкой, удаляет невидимые символы, нормализует пробелы, декодирует HTML-сущности и удаляет предусмотренные кодом HTML-теги в `text`. Заголовок и содержание объединяются в `document`. Регистр, числа и отрицания сохраняются. Финальное обучение использует все строки train.

## 2. Валидация

В исследовательских экспериментах использовалось фиксированное разбиение: приблизительно 80% запросов для обучения и 20% для валидации, `seed=42`.

- Все кандидаты одного запроса относятся к одной части выборки.
- Совпадающие нормализованные формулировки запросов объединяются при разбиении.
- При создании разбиения предусмотрена стратификация по числу релевантных кандидатов: 1, 2, 3, 4+; она применяется при достаточном числе групп каждого типа.
- Из обучающей части исключаются фрагменты, пересекающиеся с валидацией по `document_id` или тексту.
- В валидации сохраняются все исходные кандидаты каждого запроса.
- Состав разбиения сохраняется и повторно используется в экспериментах.

| Часть выборки | Количество пар |
|---|---:|
| Обучение после исключения пересечений | 23 801 |
| Валидация | 6 300 |

Валидация содержит **609 запросов**. При вычислении NDCG@10 кандидаты сортируются по прогнозу по убыванию, а при равных прогнозах — по строковому `id` по возрастанию. IDCG определяется по всем кандидатам исходного запроса. Предварительный отбор кандидатов не выполняется.

Для бинарной релевантности выигрыш `2^relevance - 1` совпадает с `relevance`. DCG суммируется по первым десяти позициям с дисконтом `1 / log2(r + 1)`, затем делится на IDCG. Полученные значения усредняются по запросам. В проверках, где это явно контролируется кодом, каждый валидационный запрос имеет хотя бы один релевантный фрагмент; общая функция метрики возвращает ноль для запроса с нулевым IDCG.

Разбиение используется для исследования и выбора конфигурации. Итоговый ноутбук обучает выбранное решение на всём train и не зависит от сохранённого исследовательского разбиения.

## 3. Сравнение исходных моделей

Первый этап — проверка опубликованных реранжировщиков без дополнительного обучения на данных соревнования. Цель — выбрать основу для дообучения. Под «исходной» понимается готовая предобученная модель, а не случайная инициализация.

### Корректность сравнения

Модели оцениваются на одинаковых запросах, кандидатах и метках релевантности. Используются одна метрика и одинаковый порядок разрешения совпадений прогнозов. Сложные кандидаты не удаляются. Различия числовых шкал скоров не мешают сравнению: NDCG зависит от порядка документов внутри запроса.

В основной проверке вход ограничен бюджетом 512 токенов с учётом формата конкретной модели. Токенизаторы, инструкции и служебные шаблоны различаются, поэтому в этот бюджет может помещаться разный объём документа. Режимы численной точности также не полностью одинаковы. Следовательно, таблица сравнивает готовые модели в проверенных конфигурациях, а не изолированное влияние архитектуры и не максимально достижимое качество каждой модели.

**Jina v2 показала лучший исходный результат — 0.952824.** Преимущество над BGE составило 0.033863, над проверенным режимом Jina v3.5 — 0.009655. Jina v2 выбрана основной моделью для дальнейшего обучения.

### Дополнительная быстрая проверка

Отдельно проверены 100 запросов и 1 037 пар, выбранных из той же валидации с `seed=42`.

| Модель | Дообучение на данных соревнования | NDCG@10 |
|---|---|---:|
| Jina v2, сохранённая модель после BCE | Да | 0.960934 |
| Jina v3.5, совместное ранжирование кандидатов | Нет | 0.949474 |
| Yuanbao-Search/Yuanbao-Reranker-0.6B | Нет | 0.907203 |

В этой проверке документ ограничен 512 токенами отдельно от служебного шаблона. Результаты не объединяются с основной таблицей из-за другого состава запросов и другого режима ограничения длины. Дообученная Jina приведена как практический ориентир; её сравнение с исходными моделями не изолирует эффект архитектуры.

## 4. Эксперименты с дообучением

Первоначальное дообучение выполнялось с бинарной кросс-энтропией (BCE). Модель училась предсказывать релевантность каждой пары независимо. Для выбора checkpoint использовалась NDCG@10.

| Модель и способ обучения | До обучения | После обучения | Изменение |
|---|---:|---:|---:|
| MiniLM, полное дообучение, лучший проверенный checkpoint | 0.836828 | 0.893577 | +0.056749 |
| BGE, LoRA, 1 эпоха | 0.918961 | 0.936749 | +0.017788 |
| Jina v2, полное дообучение, 1 эпоха | 0.952824 | 0.959345 | +0.006521 |
| **Jina v2, полное дообучение, 2 эпохи** | **0.952824** | **0.960276** | **+0.007452** |

Все значения относятся к полной валидации. MiniLM и BGE улучшились после обучения, но уступили дообученной Jina. Число эпох, learning rate и способ адаптации между моделями различались. Таблица показывает результаты конкретных запусков и не доказывает общее превосходство полного дообучения над LoRA.

### Выбор эпохи для Jina с BCE

| Эпоха | Validation BCE | NDCG@10 |
|---|---:|---:|
| 1 | 0.267810 | 0.959345 |
| 2 | 0.277220 | **0.960276** |

На второй эпохе BCE на валидации выросла, а NDCG@10 улучшилась на 0.000931. Поэтому среди проверенных завершённых эпох выбрана вторая. Это подтверждает необходимость выбирать checkpoint по метрике ранжирования, а не только по классификационной функции потерь.

### Проверка функций потерь

BCE рассматривает документы независимо, тогда как целевая задача требует правильного порядка внутри запроса. Поэтому следующим направлением стал переход к RankNet.

В исследовательском ноутбуке подготовлено сравнение BCE, RankNet и LambdaRank@10 из одного checkpoint Jina после двух эпох BCE. Для всех вариантов заданы одинаковые 60 обновлений, четыре запроса на обновление, последовательность запросов, `learning_rate=1e-6`, лимит 512 токенов и полная валидация. Такой протокол проверяет короткое продолжение обучения при сопоставимых условиях, а не полное независимое обучение каждого варианта.

В сохранённых выводах есть исходный результат 0.960276 и результат продолжения с BCE 0.959498. Завершённые численные результаты RankNet и LambdaRank@10 в приложенном исследовательском файле отсутствуют; неподтверждённые значения в таблицы не включены.

## 5. Итоговое решение: Jina v2 + RankNet

**Для окончательного решения выбран RankNet с полным дообучением Jina v2.** Для каждого запроса сравниваются все пары «релевантный — нерелевантный». Функция потерь усредняет `softplus(s_negative - s_positive)` по таким парам внутри запроса. Это обучает относительному порядку документов, но не оптимизирует NDCG@10 напрямую.

Финальный запуск загружает исходную предобученную Jina, а не checkpoint из эксперимента с BCE. Внешние обучающие датасеты в пайплайне не подключаются. Тестовая выборка используется только для получения предсказаний.

| Параметр | Значение |
|---|---|
| Модель | `jinaai/jina-reranker-v2-base-multilingual` |
| Ревизия | `9cfeff2df7d40d1b78e75e5e9cebec92a99813c9` |
| Способ адаптации | Полное дообучение |
| Функция потерь | RankNet |
| Финальная обучающая выборка | 31 530 пар, 3 042 запроса |
| Эпохи | 2 |
| Learning rate | `5e-6` |
| Максимальная длина пары | 512 токенов |
| Batch обучения | 1 запрос со всеми кандидатами |
| Накопление градиентов | 4 запроса |
| Документов за один проход модели | До 2 |
| Оптимизатор | AdamW |
| Weight decay | `0.01` |
| Scheduler | Линейный, warmup 10% планируемых обновлений |
| Batch предсказаний | 8 пар |
| Seed | 42 |

Две эпохи используются как рабочая настройка финального запуска. Предыдущая проверка числа эпох проводилась с BCE; оптимальное число эпох именно для RankNet отдельно не установлено.

Для каждой тестовой пары сохраняется исходный скор модели, без преобразования в вероятность. Итоговый CSV формируется в порядке `sample_submission.csv`. Проверяются идентификаторы, состав столбцов и отсутствие NaN/Inf.

## 6. Среда и зависимости

Исследовательские запуски выполнялись в **Google Colab, Linux x86_64, Python 3.12, NVIDIA Tesla T4**, около 14.6 GiB доступной видеопамяти. В исследовательском ноутбуке зафиксированы PyTorch `2.14.1+cu130`, Transformers `5.22.1` и Accelerate `1.15.0`.

Файл `require.txt` содержит зафиксированные версии прямых и транзитивных зависимостей для **Linux x86_64 и Python 3.12**. Он подготовлен на основе версий основных библиотек из ноутбуков и результата разрешения зависимостей. Это подготовленная конфигурация для проверки воспроизводимости, а не полный `pip freeze` исходной сессии Colab. Дополнительные версии, не зафиксированные в исходных выводах, выбраны при подготовке этого файла.

Включены зависимости модели, токенизатора и ядра Jupyter. CUDA-библиотеки, входящие в разрешённый набор PyTorch для Linux, также перечислены. Драйвер NVIDIA устанавливается отдельно и не входит в Python-зависимости. `peft`, `scikit-learn` и `sentence-transformers` не нужны для финального пайплайна RankNet и не включены как прямые зависимости.

Описание пакетов: [PyTorch](https://pypi.org/project/torch/2.14.1/), [Transformers](https://pypi.org/project/transformers/5.22.1/), [Accelerate](https://pypi.org/project/accelerate/1.15.0/).

## 7. Воспроизведение и размещение файлов

По условию сдачи в корне открытого репозитория должны находиться ровно три файла:

| Файл | Назначение |
|---|---|
| `решение.ipynb` | Итоговая предобработка, обучение RankNet и предсказания |
| `require.txt` | Зависимости с версиями; именно это имя указано в условии |
| `README.md` | Описание решения, история экспериментов и запуск |

Предоставленный отдельно `requirements.txt` является идентичной копией `require.txt` с распространённым названием. Для сдачи следует использовать `require.txt`, не добавляя его копию четвёртым файлом в корень репозитория.

### Порядок запуска

1. Выбрать среду **Linux x86_64, Python 3.12, GPU NVIDIA с поддержкой CUDA**. В Colab включить GPU в настройках среды выполнения.
2. В свежей среде установить зависимости до импорта ML-библиотек:

   ```bash
   python -m pip install -r require.txt
   python -m pip check
   ```

   В ячейке Colab/Jupyter можно использовать `%pip install -r require.txt`. Если пакеты уже импортировались до установки, перезапустить ядро/среду выполнения.

3. Разместить архив `amml-ranking-competition-2026.zip` в текущей рабочей папке ядра. В стандартном Colab это `/content`. Ноутбук также ищет архив в родительской папке, в `ROOT/data` и в предусмотренных кодом путях Kaggle. Указание «рядом с ноутбуком» предполагает запуск ядра из папки репозитория.
4. Открыть `решение.ipynb` и выполнить все ячейки сверху вниз. Существующая ячейка установки основных библиотек использует те же закреплённые версии Transformers, Accelerate, Einops и TorchAO.
5. Дождаться завершения двух эпох и предсказаний. Путь к CSV выводится в последней ячейке.

Исходная модель загружается из Hugging Face при первом запуске и далее используется из кеша. Для первого запуска нужен доступ к загрузке весов и кода модели. Запросов на подключение Google Drive и автоматического скачивания файлов через браузер нет.

### Временные файлы и повторный запуск

В ноутбуке задано:

```python
ROOT = Path(tempfile.gettempdir()) / "pmmo_ranknet"
CACHE = str(ROOT / "hf_cache")
```

| Данные | Расположение |
|---|---|
| Кеш исходной модели и токенизатора | `ROOT/hf_cache` |
| Checkpoint после каждой эпохи | `ROOT/runs/jina_all_ranknet_html_2ep_v1/checkpoint-*` |
| Итоговые предсказания | `ROOT/runs/jina_all_ranknet_html_2ep_v1/submission_ranknet.csv` |

CSV из архива читаются непосредственно в память, без сохранения распакованных копий. Параметры `save_strategy="epoch"`, `save_only_model=True`, `save_total_limit=2` оставляют до двух комплектов весов и сопутствующих файлов; состояния оптимизатора не сохраняются. `ROOT` не требует существования перед запуском: нужные каталоги создаются кодом сохранения результатов.

Если CSV уже существует, ноутбук проверяет его и пропускает обучение и инференс. Если сохранена завершённая вторая эпоха, но CSV отсутствует, выполняется только инференс. Если остались checkpoint незавершённого обучения, ноутбук останавливается с сообщением: для нового полного запуска нужно задать новый `RUN_DIR`. При изменении параметров также требуется новый `RUN_DIR`, чтобы не использовать результат предыдущей конфигурации.

В Colab временные файлы находятся на сервере, при локальном запуске — на компьютере, где работает ядро. Временная папка не является постоянным хранилищем: после её очистки веса и результаты могут исчезнуть. Дополнительный служебный кеш Hugging Face может создаваться в стандартной папке библиотеки.

## 8. Статус проверки и ограничения

- Проверены синтаксис Python-ячеек финального ноутбука и сохранность исходной логики RankNet после удаления BCE и замены путей.
- Для набора зависимостей выполнено разрешение `pip install --dry-run --ignore-installed --only-binary=:all:` на Linux x86_64 с Python 3.12.14. Это проверка установочных ограничений по метаданным, а не фактическая установка всего окружения.
- Полное обучение и инференс с подготовленным `require.txt` в чистой GPU-среде ещё не выполнены. Подтверждение работы именно с этим набором версий требует такого запуска.
- Основные результаты получены на одном фиксированном разбиении. Многократный выбор моделей по этой валидации не заменяет независимую итоговую оценку.
- Численный результат RankNet на полной валидации не сохранён в приложенном исследовательском файле. Значения BCE и RankNet не подменяются друг другом.
- Побитовое совпадение предсказаний при изменении GPU или окружения не гарантируется.

Итоговое качество соревнования определяется результатом на закрытой тестовой выборке.
